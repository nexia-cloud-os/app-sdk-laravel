# Paged import review (unreleased)

`PagedImportDecisionProvider` is an optional companion to an import pipeline. It needs the matching Core, App runtime and a future PHP SDK release; this source change alone does not enable the workflow. Existing complete `ImportPlan` implementations remain supported. A pipeline that must still load on an older SDK can expose `pagedDecisionProvider(?string $batchId): ?object` as a lazy factory and keep the provider outside scanned contribution locations. Return `null` for an older batch that has no paged snapshot.

`decisionSummary` returns a bounded summary, an opaque immutable analysis generation, the current selection revision and completion state. Its `plan` contains only `blocking_issue_keys` and `blocking_issue_params`; decisions, options, sections, section items and reference issues are obtained through `reviewPage`. A page returns at most the requested 1–100 items, an exact total and an opaque next cursor of at most 2048 bytes. Each cursor must identify its batch, generation, collection and collection key; bind it to the selection revision when staged choices can change that collection. Changes to the source, mapping, or analysis invalidate the old generation. Only `choice` and `multiple_choice` decisions are supported by this paged contract; keep `row_acceptance` on the complete legacy plan path.

Decision descriptors retain their normal type, key, translated label and blocking metadata, plus the option total. Option entries retain their value and translated label and include `selected`. A section descriptor has a stable `key`, heading and item total. Section items and reference issues retain their existing plan shapes. Report a disclosure's full count and content fingerprint; one explicit acceptance covers exactly that fingerprint. Reading a page never selects an option or accepts a disclosure.

`stageDecision` applies one bounded action: `set` (one value), `clear`, `select` or `unselect` (1–100 values), `select_all`, `clear_all`, or `accept_notice`. A change contains `decision_key`, `action`, optional `values` and optional `notice_fingerprint`. Validate every value against the frozen candidate set. Only an explicit user action may select all; notice acceptance must match the full disclosed fingerprint. Apply dependent invalidation, such as clearing a target after changing its mode, inside the same transaction.

Store the selection change and the immutable operation receipt in one App database transaction. Bind them to tenant, actor, legal entity, batch and generation. On an exact `operationId` retry, compare the original payload before the current revision and return the original receipt. Reject operation-ID reuse with a different payload and reject a newly submitted stale revision as a validation failure. `decisionOperation` only reads that same receipt; `null` means its outcome is not known, not that execution failed. Do not replay an uncertain operation merely because a reply was lost.

`sealDecisions` checks that all required decisions are complete, then atomically records a replayable receipt and returns an opaque submission bound to the same ownership, generation and selection revision. The import receives it as `mapping['decisions']['__submission']`. Validate that token again when receiving, validating and applying the batch; do not treat it as permission or reconstruct all selections into one array. Changes after sealing invalidate the token. The host rechecks the selected App, actor, legal entity and runtime identity for each call.

## Read-only plan execution

A pipeline may set `supportsReadOnlyPlan` on its definition when every `import.plan` path, including the initial summary, composed pages and older batches, can run in a read-only PostgreSQL snapshot while another job is writing. Use ordinary reads on the runtime connection. Initialize review records during a write operation and keep row locks, file writes, host mutations and other side effects out of plan execution. Leave the capability at its default if any plan needs these operations. Existing catalogs omit the field. Enable it after the host and runtime support the declaration.

Work handlers and import pipelines can declare an optional `workConflictGroup`. Use the same group within an App for operations that may mutate overlapping records or produce conflicting external effects. A distinct group permits concurrent execution, so audit the complete handler, including callbacks and retries, before declaring it independent. Omit the group when its effects are unknown. Choose a stable lowercase key of at most 64 characters. Start with a letter and use letters, digits or hyphens. Keep identifiers consistent across releases while earlier work may still run.
